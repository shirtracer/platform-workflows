# Secrets

Two kinds reach your app, both as **files** under `/run/secrets/<NAME>` (one value, no trailing
newline), never as environment variables. A service gets a file only if its `secrets:` list in
`deploy/compose.yaml` names it, and every name needs a top-level `secrets:` entry
`file: ${APP_SECRETS}/<NAME>` ([The contract](contract.md#secrets)).

## The platform's credentials

Generated by the platform for the services in `platform.yaml`; you never see or set them:

| `platform.yaml` | Files |
|-----------------|-------|
| `services.postgres` | `POSTGRES_PASSWORD`, `DATABASE_URL` |
| `services.redis: true` | `REDIS_PASSWORD`, `REDIS_URL` |
| `services.s3: true` | `S3_ACCESS_KEY`, `S3_SECRET_KEY` |
| `auth: oidc` | `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` |

The admin can replace them (e.g. after a leak); your app is restarted and reads the new values.
Read the files when you connect, not once at build time.

## Your own secrets

Names in `platform.yaml` → `secrets`; values in GitHub:

- **Recommended: the Environment `production`** (Settings → Environments), with deployment
  branches limited to `main`. Only the deploy job on `main` receives them.
- **Alternative: repository secrets** (Settings → Secrets and variables → Actions). Every
  workflow on every branch of the repository can read them, so anyone who can push a branch can
  get at them. A name set in both places takes the Environment's value.

Either way: whoever can push to `main` can change your app and read its secrets at runtime; give
write access only to people you'd trust with them. Never print secret values in your own workflow
steps or logs.

The caller in `.github/workflows/deploy.yml` passes your secrets with
`PLATFORM_SECRETS: ${{ toJSON(secrets) }}`; keep it (`secrets: inherit` would pass nothing to the
platform's workflow, which belongs to another owner). Only the names listed in `platform.yaml` are
sent.

## Changing a secret

Change the value in GitHub, then **push a commit** (an empty one is fine:
`git commit --allow-empty -m "rotate secret" && git push`). Re-running an old workflow run uses
the old commit and doesn't restart your app. A removed name loses its file with the next deploy.
